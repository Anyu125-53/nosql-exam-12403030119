==================== 数据完整核验预期 ====================
seq 键前缀: exam:12403030119:seq:<i>   (i=1..1419, 共 1419 条)

值格式: value-12403030119-<i>

抽样核验:
  第 1 条:    seq=value-12403030119-1    pipe=value-12403030119-1    一致=True
  第 100 条:  seq=value-12403030119-100  pipe=value-12403030119-100  一致=True
  第 1419 条: seq=value-12403030119-1419 pipe=value-12403030119-1419 一致=True

预期: 两组 key 数量均为 1419，抽样值与预期一致。

==================== 结论与原因分析 ====================
预期结论: 在本地/同机 Redis 环境下，Pipeline 通常显著快于逐条写入，
因为减少了网络往返 (RTT) 次数。逐条写入需 1419 次 RTT，
Pipeline 分批后仅 15 次 RTT。

若实测差异不明显或 Pipeline 更慢，可能原因:
  1. 本地/同机网络开销极小 (loopback), RTT 本就在微秒级, 优势被稀释;
  2. 每条 SET 命令体积极小, 单条命令执行本身就很快;
  3. 批大小 Q=100 可能不是最优值, 需调整尝试;
  4. redis-py 客户端序列化/缓冲开销在小命令下占比相对较高;
  5. 系统抖动 (CPU 调度、缓存命中、后台进程) 影响短耗时测量精度;
  6. Pipeline 批次内命令需全部序列化后一次性发送, 客户端缓冲延迟可能抵消收益。
